# tg v3 — Transport Generator (github.com/seniorGolang/tg/v3)

Контракт-first кодогенератор для Go-сервисов на gofiber. Пишешь Go-**интерфейс**
с `// @tg ...` аннотациями; плагин **tgp-go** (WASM, wazero runtime) генерирует
транспортный слой (fiber server, Go/TS клиенты, swagger) через `tg server`.
Бизнес-логику и персистентность пишешь сам.

**Проект МИГРИРУЕТ с v2 на v3.** v3 module path: `github.com/seniorGolang/tg/v3`
(суффикс `/v3` обязателен — без него модуль неразрешим на Go proxy). Требует
**Go 1.26+**. Codegen запускается как WASM-плагины через пакет `tgp-go`.
Старая v2-команда `tg transport --services ...` **НЕ существует в v3** —
используй `tg server -o internal/transport`.

**Имя репо обманчиво:** `ducalis-tg` ≠ Telegram. «tg» = Transport Generator.
Telegram-бота в проекте НЕТ.

## Environment (уже в snapshot mcd-base после пересборки)

- Go 1.26.x at `/usr/local/go/bin/go` (symlink → `/usr/local/bin/go`).
- `tg` v3 CLI at `/usr/local/bin/tg` (`tg --version`).
  Установлен: `go install github.com/seniorGolang/tg/v3/cmd/tg@latest`.
- плагины `tgp-go`: `astg` (@tg-парсер, обязателен) + `server` (Fiber server
  generator), установлены через `tg pkg add https://github.com/seniorGolang/tgp-go:<name>`.
  Проверка: `tg pkg list` → показывает `astg` + `server`.
- встроенные agent-skills: входят в состав tg v3 (NB: `tg skills install` НЕ существует
  как команда в tg v3.0.x — плагины tgp-go дают нужный codegen).

Подтверди перед кодингом: `go version` (1.26.x), `tg --version`, `tg pkg list`.

## ⚠️ Project rule: tg v3 codegen — ОБЯЗАТЕЛЬНО (не опционально)

**Это жёсткое требование, не предпочтение.** HTTP-транспорт ДОЛЖЕН генерироваться
через tg v3 toolchain (`tg server`). **НЕ** пиши ручные `fiber.New()` +
`app.Get/Post` для контрактных эндпоинтов — это #1 failure mode (откат на
ручной fiber «потому что tg недоступен» — tg ДОСТУПЕН, проверь `tg --version`).

Каждый HTTP-эндпоинт:
1. определяется как метод `// @tg`-аннотированного Go-интерфейса в `pkg/contract/`, затем
2. fiber-транспорт ГЕНЕРИРУЕТСЯ через `tg server -o internal/transport`.

Только бизнес-логика (реализация контракта в `internal/service/`) и
postgres-репозитории (`internal/storage/postgres/`) — hand-written. HTTP-wiring
(роутинг, парсинг запросов, сериализация, fiber-app) — целиком из `tg server`.

**Module path ДОЛЖЕН включать `/v3`:** `github.com/seniorGolang/tg/v3`. Без
суффикса `/v3` модуль резолвится в ничего на Go proxy → ложный вывод «tg
недоступен». tg установлен — `tg --version` и `tg pkg list` доказывают это.

## Layout (целевой, после миграции)

```
pkg/contract/              ← ИСТОЧНИК ПРАВДЫ (Go-интерфейсы с // @tg)
  task.go                  ← TaskService
  workspace.go             ← WorkspaceService + AuthService + Member/User/Integration
  integration.go           ← IntegrationService
pkg/types/                 ← доменные типы/DTO (с // @tg desc=... тегами)
internal/transport/        ← СГЕНЕРИРОВАННЫЙ v3 транспорт (tg server -o)
                             [tracer/, context/, viewer/ — hand-written, НЕ трогать]
internal/service/          ← бизнес-логика (реализация контрактов)
internal/storage/postgres/ ← репозитории (pgxpool)
migrations/init.sql        ← DDL
```

**ВАЖНО про текущее состояние:** старый v2-сгенерированный транспорт
(VersionTg=v2.3.95) УДАЛЁН. `internal/transport/` сейчас содержит только
hand-written поддиректории (`tracer/`, `context/`, `viewer/`) — топ-level
сгенерированные файлы отсутствуют и должны быть регенерированы `tg server`
ПЕРВЫМ шагом миграции (см. PRD).

## Контракт — v3 annotation vocabulary

Контракт — plain Go interface. Жёсткие правила генератора:
- первый аргумент — всегда `context.Context`;
- последнее возвращаемое — всегда `error`;
- все прочие аргументы И возвращаемые значения **именованы**;
- строка `// @tg ...` —直接 над interface или method.

Текущие v2-аннотации ducalis-tg (`http-method`, `http-path`, `http-path-params`,
`http-prefix`, `tag`, `jsonRPC-server`, `summary`, `desc`) в основном совместимы
с v3, но проверь exact-синтаксис через `tg plugin doc astg` после регенерации.
v3 пример (каноничный формат):

```go
// @tg http-server log metrics trace
type TaskService interface {
    // Create creates a new task.
    //
    // @tg http-method=POST http-path=/ http-success=201
    Create(ctx context.Context, req types.CreateTaskRequest) (task *types.Task, err error)
}
```

| Tag | Значение |
|---|---|
| `http-server` / `jsonRPC-server` | включить transport на interface |
| `log` `metrics` `trace` | включить middleware на interface |
| `http-method=POST` | HTTP-метод |
| `http-path=/tasks/:id` | route + path params |
| `http-prefix=api/v1` | опц. prefix |
| `http-success=201` | success status (default 200) |
| `desc=...` / `summary=...` | docs (swagger) |
| `required` | non-zero validation |

## Codegen (v3 plugin workflow — НЕ `tg transport`)

Транспорт строит плагин **tgp-go**. Контракты в `pkg/contract/`; codegen —
подкоманда `tg` (НЕ `go generate`, НЕ `tg plugin run`). Требует `go.mod` в корне.

```bash
tg server    -o internal/transport         # Fiber server (ОБЯЗАТЕЛЬНО)
tg client-go -o pkg/client/go              # опц.: typed Go client (для тестов!)
tg client-ts -o pkg/client/ts              # опц.: TypeScript client
tg swagger   -o api/swagger.yaml           # опц.: OpenAPI 3.0
# contracts dir: укажи через --contracts-dir pkg/contract (или какой v3 ждёт)
```

Inspect флагов/аннотаций плагина: `tg plugin doc server`, `tg plugin doc astg`.
Re-run `tg server -o internal/transport` после **каждого** изменения контракта.
Коммить сгенерированное дерево (НИКОГДА не редактируй руками).

## Что НЕ делать (Never)

1. **НЕ** пиши ручные fiber-роуты/handlers/`fiber.New()`/`app.Get/Post` для
   контрактных эндпоинтов. Это #1 failure mode — откат на ручной fiber.
2. **НЕ** используй v2 (`tg transport --services`) — проект на v3 (`tg server`).
3. **НЕ** импортируй `github.com/seniorGolang/tg/v3/skills` — этот пакет НЕ
   существует в v3.0.5 (importable только `cmd/tg`). Если пиннишь toolchain в
   build-tagged `tools.go`, импортируй `github.com/seniorGolang/tg/v3/cmd/tg` —
   никогда `.../skills`, `.../agent` и пр. После tools.go: `go mod tidy`; если
   не резолвится — пакет не существует.
4. **НЕ** редактируй файлы в `internal/transport/` (top-level, сгенерированные)
   и `pkg/client/` руками — они затрутся при `tg server`/`tg client-go`.
   `tracer/`, `context/`, `viewer/` — hand-written, их можно править.
5. **НЕ** пропускай регенерацию `internal/transport` после правки `// @tg`.
6. **НЕ** доверяй путям в Makefile (`pkg/contract/public|admin|internal`) —
   сверяйся с `ls pkg/contract/` (реально плоско).

## go mod tidy под прокси (важно для VM)

`go mod tidy` под tg v3 может падать на checksum-mismatch/missing go.sum.
Рабочая инкарнация (доказано в test-todo2):

```bash
GONOSUMDB=off GONOSUMCHECK=* GOPROXY=https://proxy.golang.org,direct go mod tidy
```

`proxy.golang.org` работает; `GOPROXY=direct` падает на gnutls TLS. Некоторые
модули (напр. `github.com/cloudflare/circl` через go-git/v5, транзитивная
зависимость tg) отдаются только с `storage.googleapis.com` — он в allowlist.

## Контракт → сервис → репозиторий (поток данных)

```
pkg/contract/task.go:TaskService (interface, // @tg-аннотации)
        │  tg server -o internal/transport  (генерация)
        ▼
internal/transport/ (сгенерированный v3 сервер/роутинг/jsonrpc)
        │  внедряется через transport.New(...) в main.go
        ▼
internal/service/task.go:TaskService (бизнес-логика, реализует contract)
        │  зависит от TaskRepository (interface в service/)
        ▼
internal/storage/postgres/repositories.go (SQL над pgxpool)
```

См. `service-wiring.md` — как соединить это в `cmd/server-*/main.go` ПОСЛЕ
регенерации транспорта.

## Verification gate (модуль кормит VERIFY-фазу loki)

Перед завершением фичи — ВСЁ должно пройти, по порядку:
- `go mod tidy` clean;
- `go vet ./...` clean;
- `go build ./...` clean;
- **`tg pkg list` показывает `astg` + `server`** И **`internal/transport/`
  существует и создан `tg server -o internal/transport`** (hard gate —
  hand-written транспорт = задача не сделана);
- **`github.com/seniorGolang/tg/v3` — реальная строка в `go.mod`** (доказывает
  что tg подключён, не обойдён);
- `go directive` = `go 1.26` (tg v3 требует 1.26+);
- тесты (см. tdd-rules.md);
- сервис биндит `0.0.0.0:<port>` (НЕ 127.0.0.1 — см. service-wiring.md).
